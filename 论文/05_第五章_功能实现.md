## 5.1 系统登录与权限管理模块的实现

### 5.1.1 用户登录与 JWT 令牌认证的实现

系统登录页面基于 Vben Admin 框架构建，页面中央呈现登录卡片，包含用户名输入框、密码输入框及登录按钮，整体风格简洁统一，符合管理后台的视觉规范。用户填写凭据后，前端对输入内容进行非空与格式校验，校验通过后通过 Axios 以 POST 方式将用户名与密码提交至后端接口 `/api/v1/auth/login/`。登录成功后，系统在页面顶部展示欢迎提示，并自动跳转至仪表盘主界面；若认证失败，则在表单下方显示相应的错误提示信息。页面实现如图5.1所示。

【图5.1 用户登录页面】

后端登录视图在接收到请求后，首先从请求体中提取用户名与密码字段，调用 Django 内置的 `authenticate()` 函数完成身份验证，其内部通过 `check_password()` 对数据库中存储的加盐哈希密码进行比对。认证通过后，视图使用 SimpleJWT 库的 `RefreshToken.for_user()` 方法为该用户生成一对令牌：AccessToken（默认有效期较短，约为1小时）与 RefreshToken（有效期较长，约为7天）。生成的两枚令牌随 HTTP 200 响应一并返回给前端。前端在 Pinia store 中将 AccessToken 与 RefreshToken 持久化存储，并在 Axios 请求拦截器中为每次后续请求的 Header 自动附加 `Authorization: Bearer <accessToken>`。当 Axios 响应拦截器捕获到 HTTP 401 状态码时，系统会自动携带 RefreshToken 向 `/api/v1/auth/token/refresh/` 发起静默刷新请求，刷新成功后无缝重放原始请求，从而实现用户无感知的 Token 续期机制。相关代码如图5.2所示。

### 5.1.2 RBAC 权限控制与动态菜单下发的实现

权限管理页面提供角色列表、菜单树配置与权限规则三个子模块的管理界面。角色管理以表格形式呈现所有角色，支持新增、编辑与删除操作；菜单树配置页以层级树形结构展示全部菜单节点，管理员可通过复选框为角色勾选可见菜单；权限规则页展示各角色对应的 API 访问规则，包含请求方法与 URL 匹配模式。页面实现如图5.3所示。

【图5.3 RBAC 权限管理页面】

用户登录完成后，前端随即调用 `/api/v1/rbac/menus/` 接口获取当前用户的菜单树。后端视图通过 `request.user` 关联查询 `rbac_userrole` 表，获取用户所属的所有角色，再经 `rbac_role` → `rbac_role_menus` → `rbac_menu` 的关联链路，汇总出该用户有权访问的全部菜单节点，以树形结构序列化后返回。前端收到菜单数据后，Vben Admin 的全局路由守卫 `beforeEach` 钩子依据菜单列表动态注册路由，未包含在返回菜单中的路由路径即使被手动输入也无法激活对应页面组件，从而在前端层面形成路由隔离。在后端层面，系统实现了自定义 API 权限中间件，每个请求到达时，中间件遍历请求用户所关联角色的全部 `rbac_role_permissions` 记录，将当前请求的 HTTP Method 与 Path 与权限规则中的 `url_pattern` 进行正则匹配，若未命中任何规则则直接返回 HTTP 403 响应，杜绝越权调用的可能。相关代码如图5.4所示。

## 5.2 仪表盘模块的实现

仪表盘页面是用户登录后首先看到的总览界面，整体采用栅格布局，分为顶部统计区、中部图表区两大区域。顶部排列四张统计卡片，依次显示当前接入的 PVE 节点数量、系统累计消耗的 AI Token 数、已创建实验总数及注册用户总数，每张卡片附有对应的矢量图标与趋势指示。中部左侧为 ECharts 渲染的双轴组合图表，以柱状图展示近14天每日 AI Token 消耗量（对应左 Y 轴），以折线图展示同期调用次数（对应右 Y 轴），二者共享同一 X 轴时间轴；右侧并排展示三个圆形进度条，分别代表当前 PVE 节点的 CPU 使用率、内存使用率与磁盘使用率，进度条颜色随使用率阈值动态变化，低负载显示绿色、中等负载显示橙色、高负载显示红色，直观反映资源压力状况。页面实现如图5.7所示。

【图5.7 仪表盘页面】

前端在页面挂载时通过 `Promise.allSettled` 并发发起四个统计接口请求，该方式确保任意单个接口失败不会影响其余卡片的数据展示。节点资源使用率数据来自接口 `/api/v1/pve/nodes/{server_id}/{node_name}/monitor/?timeframe=hour`，后端接收请求后，以反向代理的方式向目标 PVE 服务器的 `/api2/json/nodes/{node}/rrddata` 接口发起请求，解析返回的 RRD 时序数据中的 `cpu`、`mem`、`disk` 指标，取最新一条记录计算实际使用率后返回给前端。ECharts 图表在初始化时传入双 Y 轴配置对象，柱状图系列与折线图系列分别绑定至左侧与右侧 Y 轴刻度，并在 `tooltip` 中统一格式化显示两项指标的数值，方便管理员对比分析。相关代码如图5.8所示。

### 5.3.1 PVE 服务器管理与虚拟机列表的实现

PVE 服务器管理页面以表格形式列出已接入平台的所有 PVE 服务器，展示服务器名称、主机地址、端口号及当前连接状态等信息。每行末尾的操作列提供"编辑"与"连通性测试"按钮，点击"连通性测试"后按钮进入 loading 状态，待后端验证完毕后在状态列更新结果图标。添加新服务器时弹出抽屉表单，填写主机、端口、认证凭据等信息后提交保存。虚拟机列表页展示当前所有已同步的 KVM 虚拟机记录，字段包括 VMID、所属服务器、所属节点、虚拟机名称、运行状态（以 Tag 组件着色区分 running/stopped）、CPU 核数、内存容量与磁盘大小；列表顶部提供"同步 PVE"按钮，点击后触发全量同步任务。页面实现如图5.9所示。

【图5.9 PVE 服务器管理与虚拟机列表页面】

连通性测试接口接收服务器 ID 后，后端取出该记录的主机与端口信息，使用系统内置的 PVE Session 向目标服务器的 `/api2/json/nodes` 端点发起 GET 请求，若响应状态码为 200 则判定连通正常并更新数据库中的 `status` 字段为 `online`，否则将错误原因写入响应体并将状态置为 `offline`，返回给前端展示。虚拟机同步逻辑由后端视图遍历数据库中所有处于激活状态的 `PveServer` 记录，逐一向其每个节点的 `/api2/json/nodes/{node}/qemu` 接口发起请求，将返回的虚拟机列表与数据库 `pve_virtualmachine` 表进行比对：若 VMID 不存在则创建新记录，若已存在则更新名称、状态、CPU、内存等字段，最终返回包含 `created` 与 `updated` 数量的汇总结果。相关代码如图5.10所示。

### 5.3.3 虚拟机 noVNC 图形控制台的实现

虚拟机图形控制台嵌入在虚拟机详情页的控制台 Tab 中，页面初始状态显示连接提示与"打开控制台"按钮，点击后进入连接流程，连接成功后控制台区域渲染出虚拟机的图形桌面画面。工具栏固定于控制台区域顶部，提供全屏切换、发送 Ctrl+Alt+Del 组合键、电源操作（关机/重启）等快捷按钮，方便用户在不退出控制台的情况下进行基本管理操作。页面实现如图5.13所示。

【图5.13 虚拟机 noVNC 控制台页面】

控制台连接流程分为两个阶段。第一阶段，前端激活控制台 Tab 时，向 `/api/v1/pve/vms/{id}/console/ticket/` 发起 POST 请求，后端生成一枚有效期为60秒的一次性 Ticket 并返回，该 Ticket 存储于 Django Cache中，与虚拟机 ID 和用户 ID 绑定。第二阶段，前端以 `?ticket=xxx` 为 URL 参数，发起至 `wss://.../ws/console/vm/{vm_id}/` 的 WebSocket 连接。后端 `VmConsoleConsumer` 在 WebSocket 握手阶段从 URL 参数中提取 Ticket，与 Cache 中的记录进行校验，验证通过后立即将该 Ticket 作废以防重放攻击；随后向 PVE 申请 VNC Ticket（`POST /api2/json/nodes/{node}/qemu/{vmid}/vncproxy`），利用 PVE 返回的 WebSocket URL 与端口，建立后端至 PVE noVNC WebSocket 的持久连接，并将来自前端的数据帧与来自 PVE 的数据帧进行双向透明转发。前端使用 `@novnc/novnc` 库的 `RFB` 类，将后端 WebSocket 作为传输层，最终在页面 canvas 元素上渲染出虚拟机实时图形桌面。相关代码如图5.14所示。

### 5.3.4 LXC 容器管理与 WebSSH 终端的实现

LXC 容器管理页面与虚拟机管理页面采用一致的布局结构，表格字段包括容器 ID、所属服务器、所属节点、容器名称、运行状态、CPU 与内存配置等。详情页同样采用竖向 Tab 导航，差异在于控制台 Tab 使用基于 xterm.js 的命令行终端界面而非 noVNC 图形界面。xterm.js 终端区域占据控制台 Tab 的主体空间，工具栏提供主题切换（VS Code Dark、Monokai 等预设主题）、字体大小调节与清屏按钮。页面实现如图5.15所示。

【图5.15 LXC 容器管理与 WebSSH 终端页面】

WebSSH 实现流程与 noVNC 类似，同样先通过 REST 接口申请一次性 Ticket，再建立至 `wss://.../ws/console/lxc/{lxc_id}/` 的 WebSocket 长连接。后端 `LxcConsoleConsumer` 完成 Ticket 验证后，使用 Paramiko（`asyncssh`）库向容器对应的 IP 地址发起 SSH 连接，认证成功后开启一个交互式 Shell session，并为其分配伪终端（PTY）。消费者在两条异步协程中分别处理输入与输出：收到来自前端 WebSocket 的键盘输入字节时，直接写入 SSH channel 的 stdin；SSH channel 的 stdout 与 stderr 产生新数据时，立即通过 WebSocket 推送至前端。前端 xterm.js 配置了 `FitAddon` 以根据容器尺寸自动调整终端行列数，配置了 `WebLinksAddon` 以识别并高亮输出中的 URL 链接；通过 WebSocket 的 `onmessage` 事件将接收到的字节流调用 `terminal.write()` 写入终端画布，用户在 xterm.js 中的每次击键事件则通过 WebSocket `send()` 实时发往后端，实现近乎零延迟的 Web Shell 交互体验。相关代码如图5.16所示。

RAG 向量化流程由 Celery Worker 异步执行：任务启动后首先将 `chat_aiknowledgeindexstatus` 表中对应记录的状态更新为 `processing`，随后读取指导书文件内容，按 `chunk_size=500`、`overlap=50` 的滑动窗口策略将文本切分为多个片段，逐批调用 Embedding 模型接口生成向量，最终将文档块文本与对应向量写入 ChromaDB 向量数据库的专属 Collection 中，并将状态更新为 `done`，记录分块总数；若执行过程中发生异常则将状态置为 `failed` 并记录异常信息。智能体在处理用户问题时，若 `enable_rag=True`，后端将用户问题文本同样转换为向量，在 ChromaDB 中执行相似度检索，取 Top-K 个最相关文档块，将其内容拼接至 System Prompt 上下文后再提交给大模型，从而使回答更贴合平台实际文档内容，有效降低模型幻觉。相关代码如图5.26所示。
