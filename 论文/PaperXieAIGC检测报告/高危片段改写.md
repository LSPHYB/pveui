## SEG1 — 摘要第一段

虚拟化和云计算技术现在已经很普遍了，各行业对 IT 资源的管理要求也随之水涨船高。Proxmox VE 在私有云这块确实有它的地位，但碰到多租户隔离、业务定制、界面设计这些问题，原生平台就有些力不从心了。本文基于 Vue 3 和 Django 5 搭建了一套云管平台，把 PVE 的操作门槛往下拉了一截，同时也针对教学场景做了功能延伸。

---

## SEG2 — 摘要技术架构

整个系统按前后端分离来做。前端用 Vue 3 的组合式 API 配合 Vite，跑在 Vben Admin 的架子上，做出来的管理界面响应比较快；网络拓扑那块用的是 LogicFlow，终端接了 xterm.js 和 noVNC。后端是 Django 5 加 DRF，接口走 RESTful 规范，数据落到 MySQL 里。物理资源调度通过 PVE REST API 和 SSH 来做。控制台的实时通信用 ASGI 异步架构配合 WebSocket，延迟控制得还不错。

---

## SEG3 — 摘要四大功能

系统做了四块主要功能。虚拟机和容器的管理贯穿从创建到销毁的全流程，网络资源能用拓扑图可视化分配出去。权限这块用 RBAC 模型搭了一套多级管控体系，每个接口的操作都有日志记录在案。教学模块按教师和学生两个角色来设计——老师发实验环境，学生用 Markdown 写报告提交。最后还加了大语言模型，配合 RAG 把实验指导书检索进来，学生遇到问题可以直接问。

## SEG5 — 研究背景

传统物理服务器有一个老问题：资源利用率上不去，扩容也麻烦。云计算和虚拟化出来之后，这个局面才有所改观，高可用、弹性伸缩这些能力让它逐渐成了现代 IT 基础设施的标配。但高校和中小企业的情况比较特殊——预算紧、运维人手少、硬件就那些，实验环境还得随时建随时收。大厂的企业级私有云方案部署流程复杂、吃资源，往往很难直接套用。所以针对这类场景，搭一套轻量、好管、能自助操作的私有云平台，还是有实际价值的。

---

## SEG6 — PVE 背景

在开源虚拟化这个领域，Proxmox VE 算是比较有存在感的一个选择。它基于 Debian 做了深度定制，KVM 和 LXC 都内置支持，带一个 Web 管理界面，集群调度、网络配置、存储挂载都能在上面搞定。不过 PVE 的原生面板是给有技术背景的运维人员设计的，关注点在底层硬件资源上。非专业用户用起来有门槛，而且一些业务层面的逻辑它也没法直接支持。

---

## SEG7 — 研究意义

本文结合上面说的这些问题，用 Vue 3 + Django 5 的技术栈从头设计了一套 PVE 云管理平台。技术层面，把原来比较散乱的 PVE 底层 API 重新封装了一遍，用前后端分离的方式把界面做得更直观。终端交互走 ASGI 异步加 WebSocket，实时性明显好了不少，一般用户上手不需要懂 PVE 的底层逻辑。场景层面，这套系统不只是管资源——它把实验下发、报告回收这些教务流程也一并整合进来了。再加上 RAG 驱动的大模型问答，学生遇到实验问题可以直接在平台里问，不用去翻文档。

---

## SEG8 — Pinia

Pinia 是 Vue 现在官方推荐用的状态管理库，用过 Vuex 的会发现它轻量很多。它把 Mutation 这一层直接去掉了，只剩 State、Getters 和 Actions 三个概念，逻辑上清晰不少。每个 Store 独立定义，天然就能做代码分割。TypeScript 支持也做得比较彻底，类型推断不用额外写声明，写代码时提示很准，编译期就能发现问题。

---

## SEG9 — xterm.js

xterm.js 是一个跑在浏览器里的终端模拟器，支持 VT100/VT220 标准的 ANSI 转义序列，颜色渲染、光标控制、滚动缓冲这些都能正确处理。它有插件机制，文本搜索和 WebGL 加速渲染都能按需挂进去。配合 WebSocket 使用，就可以在网页上直接开一个延迟低、手感接近原生终端的远程 Shell 窗口。

---

## SEG10 — noVNC

noVNC 是纯 HTML5/JavaScript 写的 VNC 客户端，浏览器直接打开就能连远程桌面，不用装任何插件。底层走 WebSocket 把 RFB 协议帧传过来，用 Canvas 渲染出画面。键盘、鼠标输入都能正常映射，剪贴板也能同步。

---

## SEG11 — Django ORM

Django ORM 是框架自带的数据库抽象层。开发时用 Python 类定义模型，ORM 负责把它翻译成建表语句；操作数据时写的是 Python 对象，ORM 在背后生成参数化 SQL 去执行。参数化查询把 SQL 指令和数据彻底分开，SQL 注入在机制上就被堵死了。跨表关联、多对多、自引用这些复杂关系也都能简洁地表达出来。

---

## SEG12 — RESTful

REST 是一种以"资源"为中心的 API 设计风格。每个业务实体对应一个 URI，操作用 GET/POST/PUT/PATCH/DELETE 这几个 HTTP 动词来区分，响应统一返回 JSON。好处是规范可预期，前端不用猜接口行为，第三方系统接入也方便。本系统的接口设计遵循这套规范。

---

## SEG13 — JWT

JWT（JSON Web Token）是 RFC 7519 定义的一种令牌格式，由 Header、Payload 和 Signature 三段拼成。服务端收到后验签就能判断合法性，不需要去查 Session 存储——这是它无状态的核心特点。在前后端分离的场景里，JWT 一般放在请求头的 Bearer Token 里发过来，对跨域也友好。本项目用的是 djangorestframework-simplejwt，它负责 Access Token 和 Refresh Token 的签发、校验和刷新。

---

## SEG14 — ASGI

ASGI 是 Python Web 生态里 WSGI 的升级版，主要区别在于它是异步的。WSGI 每个请求都是同步阻塞的，并发高了就得多开进程或线程。ASGI 用事件循环驱动，单进程里可以跑大量协程，I/O 等待期间不会卡住别的请求。HTTP/2 和 WebSocket 这类长连接场景，ASGI 处理起来比 WSGI 顺手很多。

---

## SEG15 — Daphne

Daphne 是 Django Channels 配套的 ASGI 服务器，负责接收外部连接，然后按协议类型分发给 Django 的业务层处理。HTTP 请求和 WebSocket 长连接可以跑在同一个端口上，部署时不用分开处理，省了不少配置上的麻烦。

---

## SEG16 — PVE 认证

PVE API 的认证走票据（Ticket）机制。调用时先向 `/api2/json/access/ticket` 提交账号密码，换回两样东西：有时效限制的 PVEAuthCookie 和防 CSRF 用的 CSRFPreventionToken。之后每次请求，Cookie 和请求头里都得带上这两个，缺一不可。PVE 还支持 API Token 模式，可以给特定 Token 单独设权限范围，更适合系统间的自动化调用。

---

## SEG17 — SSH

SSH 是在不安全网络上建立加密通信的协议，服务器远程管理基本都靠它。认证和密钥协商阶段用非对称加密，握手完成之后切换成对称加密来保护后续通信。远程登录、跑自动化脚本、传文件，这些场景里 SSH 是绕不开的。

---

## SEG18 — Paramiko

Paramiko 是 Python 里最成熟的 SSH 库，功能比较全：密码认证、公钥认证、交互式 Shell、命令执行、SFTP、端口转发都支持。它基于同步 I/O，用线性的方式写跨主机运维逻辑很直观，适合批量脚本化操作这类场景。

---

## SEG19 — AsyncSSH

AsyncSSH 和 Paramiko 的 API 风格差不多，但底层全换成了 asyncio 协程，所有 I/O 都是非阻塞的。要同时维持大量 SSH 连接时，Paramiko 的同步模型会开很多线程，资源消耗比较大；AsyncSSH 直接挂在事件循环上，并发上限高，内存占用也低。在 ASGI 后端里用它，和框架的事件循环配合起来很顺。

---

## SEG21 — 操作可行性

## SEG34 — 额度管理需求

额度管理：给每个用户单独设 Token 使用上限。每次调模型都记录实际消耗（输入和输出分开算），超出配额就拒绝新的请求。

## SEG35 — 知识库管理需求

知识库管理：显示每份实验指导书的向量化状态（待处理/处理中/已完成/失败），以及分块数量和处理备注。指导书更新后，管理员可以手动触发索引重建，让知识库跟上最新内容。

---

## SEG36 — 非功能需求·安全性

安全性要求上，前后端通信统一走 HTTPS/TLS，WebSocket 用 WSS，传输层的窃听和篡改在协议层就挡掉了。身份认证用 JWT，Token 有过期时间，支持刷新；所有 API 入口都做 RBAC 校验，没权限就返回 403。控制台会话的票据是一次性的，有效期不超过 60 秒，防止被重放。PVE API Token 和 AI API Key 这类敏感内容，接口响应里不能明文带出去。数据库操作走 Django ORM，参数化查询把 SQL 注入堵了，CSRF 和 XSS 也有对应的防御。

---

## SEG37 — 非功能需求·可维护性

可维护性方面，后端按功能拆成独立的 Django App：rbac、pve、experiments、chat、audit、tasks、system，各自职责清晰，改一块不影响另一块。AI 模型端点、功能开关这类会变的配置，存在数据库的 SystemSetting 表里，管理员改了立刻生效，不用重启服务。API 接口统一了分页、过滤、搜索、排序的参数格式，前后端约定好了，联调和后续维护都省事。

---

## SEG38 — 设计原则·安全优先

**安全性优先原则**：身份认证用 JWT，需要鉴权的接口都过 RBAC 校验。WebSocket 控制台连接用一次性票据，用完即失效，防重放。PVE API Token、AI API Key 这类敏感配置，入库前加密，接口响应里不允许明文出现。

---

## SEG39 — 系统总体设计

后端的核心是基于 Django 5 + DRF 构建的业务代理层，跑在 Daphne 上，HTTP 和 WebSocket 请求都能处理。每个请求进来先过 SimpleJWT 校验和 RBAC 拦截，通过了再分发到对应的业务模块。本地数据的读写走 Django ORM；需要操作 PVE 的部分，由专门的异步代理模块转成 PVE 原生 API 调用，Ticket 和 CSRF Token 的映射、克隆这类耗时任务的状态追踪也都在这层处理。

## SEG51 — 虚拟机创建实现

创建虚拟机用向导式多步表单，用户填 CPU 核数、内存大小（MB）、磁盘大小（GB）、存储池名称和模板 VMID，提交后 POST 到 `/api/v1/pve/vms/`。后端拿到参数，向 PVE 发克隆请求，PVE 马上返回一个 UPID 任务追踪码。后端把 UPID 和新虚拟机记录存进数据库，然后交给 Celery 异步 Worker 去轮询任务状态，完成后更新虚拟机状态字段。电源操作根据传入的动作参数（start/shutdown/stop/reboot）映射到 PVE 对应的接口路径，POST 过去执行。快照列表通过 GET 请求从 PVE 拉取。

## SEG54 — WebSSH 实现

数据双向传递靠两个并行协程来驱动：一个把 WebSocket 收到的输入实时写进 SSH 通道的 stdin；另一个盯着 stdout/stderr，把输出字节流推给前端。前端这边，xterm.js 加了 FitAddon 做自适应布局，WebLinksAddon 自动解析 URL；监听到 onmessage 就调 `terminal.write()` 渲染输出，用户的键盘输入同步发回后端。整体延迟不高，交互手感接近本地终端。代码逻辑详见图5.16。

## SEG55 — 网络拓扑实现

拓扑数据由后端提供。视图收到节点名称后，向 PVE 的 `/api2/json/nodes/{node}/network` 拉取网卡和网桥配置，解析成 Cytoscape.js 需要的 nodes 数组和 edges 数组——node 带接口类型和 IP，edge 描述网桥和物理网卡的绑定关系。前端拿到数据用 `cose` 弹力布局自动排节点，不会重叠。保存拓扑时，前端调 `cy.json()` 把画布状态序列化成 JSON，POST 到 `/api/v1/pve/topologies/`，后端存到 pve_networktopology 表的 diagram_data 字段。打开已有拓扑时，URL 带上 `?id=X`，前端挂载时检测到参数就去拉对应数据，再用 `cy.json()` 反向恢复画布。相关代码如图5.18所示。

## SEG56 — 实验报告实现

学生首次进实验编辑器，后端用 `get_or_create` 为其建一条 draft 状态的 submission 记录，返回 submission ID 给前端用。Markdown 编辑器基于 marked.js 做实时预览，图片支持直接拖拽进来——前端捕获 dragover 和 drop 事件，把图片以 multipart/form-data POST 到附件接口，后端存文件并写 experiments_courseattachment 表，返回访问 URL，前端随即在光标处插入图片语法。草稿保存用 PATCH 请求把内容写进 submission.content；提交时弹二次确认，确认后 PATCH 发 `submission_status=submitted`，后端记录提交时间。

## SEG57 — API Key 加密实现

API Key 不以明文存库。保存时用 cryptography 库的 Fernet 方案加密，密文存到 `ai_apikey.api_key_encrypted` 字段；调大模型 API 时，后端实时解密还原，明文只在内存里短暂存在，不落盘。配额扣减用数据库事务加行级锁 `select_for_update()` 来保证并发安全，多个请求同时来不会把余额多扣一遍。相关代码如图5.24所示。

## SEG67 — 总结第一段

高校 IT 设施现在有向私有云转的趋势，PVE 作为开源虚拟化平台，底层能力够用。但原生面板的问题是聚焦在硬件层面，教学场景需要的业务逻辑抽象和细粒度权限管控，它做得不够。本文基于这个出发点，设计并实现了一套面向教学场景的 PVE 云管理平台，把权限体系和业务逻辑重新捋了一遍，让底层资源管理和上层教学需求能对上。

## SEG68 — 总结·权限体系

权限这块以 RBAC 为核心，结合多级组织架构和角色分类，把权限校验做到了 API 路由这个粒度。每个请求从发起到响应，自定义中间件全程记操作日志。这样数据读写有迹可查，出了问题能回溯。

---

## SEG69 — 总结·RAG 集成

AI 辅导这块用 RAG 来做。实验指导书上传后，系统把它解析并向量化存到 ChromaDB 里。学生提问时，先检索出相关上下文，拼进 System Prompt 里再送给模型。这样模型回答是基于真实的本地指导书，而不是靠自己"编"，幻觉问题少了很多，给的操作指引也更准。

---

## SEG70 — 不足·存储管理

存储管理这块目前只覆盖到本地文件系统和基础网络配置。Ceph 分布式存储在企业级高可用场景里很常用，但它的配置逻辑比较复杂，当前版本还没有做 Web 端的可视化管理，参数调整和状态监控都得直接去 PVE 原生界面操作，这块是个明显的功能缺口。

---

## SEG71 — 不足·告警机制

监控告警方面现在比较被动——用户得自己盯着仪表盘才能发现问题。虚拟机资源耗尽、容器失联、异常宕机这类突发情况，系统目前没有接钉钉或企业微信的 Webhook 推送，出了事不会主动通知人。自动化巡检也没有做，平台在无人值守状态下对集群风险基本感知不到。

## SEG73 — 未来展望内容

**与 PBS 集成实现数据灾备**：教学平台的数据安全是个实际问题，后续可以尝试对接 Proxmox Backup Server，对实验模板和重要节点做冷热备份和增量快照，建立异地容灾级别的保留策略。

**探索 Agentic AI 的运维执行能力**：现在的 AI 助手只能回答问题。往后可以在 RAG 问答的基础上，让它拥有实际操作能力——比如网络重置、服务重启这类基础操作。但要设严格的 Token 授权约束，不能让模型随便调 PVE 命令。如果能做到，学生遇到报错，AI 不只是给建议，还能帮着修一修。
