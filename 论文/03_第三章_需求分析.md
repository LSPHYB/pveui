# 第三章 需求分析

需求分析是软件工程开发流程中的核心环节，直接决定了系统能否切实解决目标用户的痛点与业务诉求。对系统需求的准确把握，既是后续架构设计与编码实现的基础依据，也是项目验收评估的主要标准。本章将从可行性分析、功能性需求与非功能性需求三个维度，对基于 Vue 3 与 Django 5 的 PVE 虚拟化管理系统进行系统化的梳理与分析。

## 3.1 系统可行性分析

可行性分析旨在评估系统开发的必要性与可行性，论证其能否在合理的技术条件、运营成本与用户接受度下实现预期目标。

### 3.1.1 技术可行性

在前端技术栈方面，Vue 3 与 Vben Admin 提供了成熟的单页应用开发框架，组件库丰富、生态完善；xterm.js 与 noVNC 均为业界广泛验证的 Web 终端与远程桌面方案，可直接在浏览器中实现 SSH 文字终端与 VNC 图形化远程桌面接入，无需安装任何客户端软件。

在后端技术栈方面，Django 5 与 Django REST Framework（DRF）具备成熟的 RESTful API 快速开发能力；Django Channels可支持基于 ASGI 协议的 WebSocket 长连接，满足控制台代理和实时监控的高并发场景。

在底层虚拟化对接方面，Proxmox VE 提供了完整的 REST API 规范与开发者文档，覆盖节点管理、虚拟机生命周期、存储、网络及任务查询等所有必要操作，消除了底层通信的不确定性。此外，SSH 通道访问所需的 Paramiko 库，以及主流大语言模型的流式 API（如 OpenAI、深度求索、月之暗面等）均有完善的 Python 生态支持，可直接集成调用。

### 3.1.2 操作可行性

原生的 Proxmox VE Web 控制台面向底层运维工程师设计，包含大量硬件抽象层术语（如 LVM-Thin 池、块设备、Ceph 仲裁等），对非专业运维背景的用户而言学习曲线陡峭，误操作风险较高。

本系统重新设计了用户界面与交互流程，使用现代化响应式 Web 设计，提供直观的向导式表单、可视化的网络拓扑编辑器，以及完善的输入校验与操作提示。与此同时，系统基于细粒度的 RBAC 角色权限机制，对不同角色的用户展示不同的菜单与操作入口：管理员可管理集群节点和资源；教师可发布和批阅实验；学生只需进入实验工作台即可直接访问分配好的虚拟机终端，无需了解底层基础设施细节。这种"以角色业务为中心"的交互设计大幅降低了不同层次用户的操作门槛，操作可行性良好。

### 3.1.3 经济可行性

本系统所选用的核心技术栈全部为开源免费方案：Debian/Ubuntu 服务器操作系统、Proxmox VE 虚拟化平台、Vue 3 前端框架、Django 5 后端框架、MySQL 数据库，无需支付商业软件授权费用。相比于 VMware vSphere 等商业虚拟化平台随规模增长的高额许可费，本方案在授权成本上具有明显优势。

在部署成本方面，系统基于标准 x86 服务器硬件运行，可充分利用高校现有机房设备或企业退役测试机器，延长硬件使用寿命，降低初期投入。长期来看，LXC 容器的轻量化资源复用特性也可显著提升硬件算力的利用率。在经济可行性上具有较高性价比。

## 3.2 功能需求分析

经过调研分析，系统的功能模块分为：仪表盘模块、系统管理模块、PVE 资源管理模块、实验教学模块以及 AI 助手模块。各模块的具体功能需求描述如下：

### 3.2.2 系统管理模块

**用户管理**：支持用户账号的创建、查询、修改与停用。用户基本信息包括用户名、姓名、邮箱及密码；支持用户头像与个人简介的维护；提供用户与角色、组织的关联管理入口。

**角色管理**：支持角色的创建与配置，包括角色名称、编码、描述及数据范围（全部/本部门/本人）设置。每个角色可关联若干菜单项与 API 权限，同一用户可被授予多个角色，其最终权限为所有角色权限的并集。

**菜单管理**：支持对系统前端菜单树的增删改查，菜单项属性包括标题、路由路径、前端组件路径、图标及排序序号，支持多层父子嵌套关系。系统根据当前用户所持角色动态下发可访问的菜单树，实现前端页面的自动裁剪。

**权限管理**：支持对 API 级权限条目的维护，每条权限记录包含权限名称、权限编码、HTTP 方法、URL 匹配模式及关联菜单，用于在后端对每个接口端点进行细粒度的 RBAC 拦截校验。

**组织管理**：支持构建多层级树形组织架构（如"院系—班级"嵌套关系），支持组织的创建、编辑与停用，以及用户与组织单元的归属绑定，并支持为用户设置主组织。

**操作日志**：系统通过后端中间件自动拦截并记录所有经过认证的 API 请求，存储字段包括操作用户、请求路径、HTTP 方法、请求参数（脱敏）、响应状态码、客户端 IP 及 User-Agent、接口耗时等。操作日志仅供查询，不允许通过接口修改或删除，支持按时间范围、用户、操作类型、请求方法和状态码进行过滤检索。

**登录日志**：专门记录用户的登录与注销事件，存储登录用户名、IP 地址、User-Agent 及操作时间，支持检索查询，为安全审计提供登录行为的追溯依据。

### 3.2.3 PVE 资源管理模块

**PVE 服务器管理**：支持添加、编辑与删除多台 PVE 物理服务器，提供一键连接测试功能。

**虚拟机管理**：提供 KVM 虚拟机的全生命周期管理能力。创建方面，支持通过向导式表单配置 CPU 核心数、内存大小、磁盘容量与存储池类型、网卡配置及操作系统类型；电源控制方面，支持启动、正常关机、强制关机、重启、挂起与从挂起中恢复操作；克隆方面，支持将虚拟机或模板克隆为新实例，可指定新 VMID 与目标节点；快照管理方面，支持快照的创建、查询、回滚与删除；备份管理方面，支持备份的创建、列表查询、从备份恢复及删除，支持备份备注与保护标志设置；此外，支持修改 CPU/内存等硬件配置参数，以及删除操作。

**存储管理**：支持查询指定 PVE 节点下的所有存储池列表及各存储的容量使用情况。

**PVE 节点监控**：提供PVE节点的详细监控视图，除仪表盘已有的实时状态数据外，还支持资源走势曲线以及基于多维阈值的健康告警列表等。

**模板管理**：复用存储管理的内容浏览接口，专门用于查看和维护各存储中的操作系统克隆模板（`vztmpl` 类型）与 ISO 镜像（`iso` 类型）资源，支持向存储上传新的模板文件。

**网络管理**：支持查询 PVE 节点上的所有物理网络接口及虚拟网桥信息，展示接口类型、关联关系及活跃状态，为管理员提供节点网络架构的查看依据。

**网络拓扑**：提供可交互的自定义网络拓扑图编辑功能。管理员可在前端画布上自由拖拽添加节点与连线，构建反映实际网络架构的拓扑示意图，并将拓扑数据持久化保存至数据库，支持后续加载与修改。

**拓扑管理**：提供与网络拓扑模块联动的拓扑视图管理能力，支持对网络拓扑结构进行信息维护以及预览

**LXC 容器管理**：提供 LXC 轻量级容器的全生命周期管理。功能与虚拟机管理类似，支持容器的创建、电源操作、克隆与删除；提供基于 WebSocket + xterm.js 的SSH 终端，使用户无需任何客户端即可直接在浏览器中与容器进行交互式命令行操作。

### 3.2.4 实验教学模块

**实验管理**：支持创建实验课程，填写课程编号、名称、描述、实验开放时间、截止时间及评分标准。实验遵循草稿→ 已发布→ 已归档的状态流转，发布前须上传指导书并设置评分标准。支持向实验上传多格式指导书文件，并提供在线预览与下载功能；文件上传后自动触发后台异步向量化索引任务，为 AI 知识库问答提供语料。支持将全部学生的提交成绩导出为 Excel 文件，包含学号、姓名、得分、是否逾期及提交状态等字段。

**提交管理**：教师可查看所有学生对各实验的提交列表，支持按实验、提交状态（草稿/已提交/已批阅）、批改状态及是否逾期进行过滤。对于状态为"已提交"的记录，教师可录入得分、整体评语及详细评分项，保存后提交状态变更为"已批阅"，并记录批改时间与批改教师；如报告存在质量问题，教师可将其退回至草稿状态并附上退回原因，学生可在修改后重新提交，系统记录累计退回次数。

**我的实验**：学生登录后进入实验工作台，仅展示当前已发布且处于激活状态的实验列表，屏蔽与学生无关的管理功能。学生进入某一实验后，系统自动为其创建草稿状态的提交记录；学生在内置 Markdown 富文本编辑器中撰写实验报告，支持上传截图等附件，支持随时保存草稿；最终确认无误后一键提交，系统记录提交时间并判断是否逾期。

### 3.2.5 AI 助手模块

**仪表盘**：展示 AI 功能的使用统计数据，包括总对话数、消息数、Token 消耗量及各模型的调用分布情况，供管理员掌握整体使用态势。

**模型管理**：管理员可配置多个大语言模型接入端点，配置项包括服务提供商、API 基础地址、模型名称、温度参数及最大 Token 数等；支持独立启用或停用某一模型配置，使系统可灵活切换不同模型服务而无需修改代码。

**API 管理**：对各模型配置所使用的 API Key 进行集中管理，支持添加、查看（Key 值脱敏展示）、轮换与删除；Key 轮换时生成新密钥并作废旧密钥，降低密钥泄露风险。

**额度管理**：管理员可为每位用户单独配置 AI 使用配额（按 Token 数量），系统记录每次模型调用的实际 Token 消耗（含输入/输出分项），并在用户超出配额时拒绝新的调用请求。

**智能体管理**：支持为特定实验课程绑定专属 AI Agent，配置其关联的模型、系统提示词（system prompt）及知识库范围，使不同实验可拥有各自定制化的问答助手角色与回答风格。

**知识库管理**：展示各实验指导书的向量化索引状态（待处理/处理中/已完成/失败），包括分块数量与处理备注；支持管理员手动触发对指定文档的索引重建，以确保知识库数据与最新指导书文件保持同步。



## 3.3 非功能性需求分析

非功能性需求是指系统在满足业务功能之外，对系统运行质量、安全性、可靠性及可维护性等方面的约束与要求。本系统的典型非功能性需求主要包含安全性需求和可维护性需求。

### 3.3.1 安全性需求

所有前后端通信须通过 HTTPS/TLS 协议加密，WebSocket 连接须使用 WSS 协议，防止传输层数据窃听与篡改。系统采用 JWT 令牌进行身份验证，令牌具有过期时间，支持刷新机制；每个 API 端点均须经过 RBAC 权限校验，未授权访问返回 403 状态码。控制台会话令牌设计为一次性使用，有效期不超过 60 秒，防止令牌重放。PVE API Token、AI API Key 等敏感凭证不得在前端响应中明文暴露。系统通过 Django ORM 进行数据库操作，规避 SQL 注入风险，并防御 CSRF 与 XSS 等常见 Web 攻击。

### 3.3.2 可维护性需求

后端按功能划分为独立的 Django App（rbac、pve、experiments、chat、audit、tasks、system），各模块职责单一、低耦合，便于独立迭代与替换。可变的业务配置参数（如 AI 模型端点、功能开关等）通过 SystemSetting 模型存储于数据库，支持管理员在不重启服务的情况下动态修改。后端 API 遵循 RESTful 设计规范，具备统一的分页、过滤、搜索与排序参数格式，降低前后端联调成本与后期维护难度。
