# 第三章 需求分析

需求分析是软件工程中极其重要且不可逾越的一环，它位于系统架构设计和核心代码编码实现之前，直接决定了最终交付的产品能否切实解决用户的痛点以及项目的整体成败。本章将从系统的可行性分析、核心功能需求与非功能性需求三个层面，对研发此基于 Vue 3 和 Django 5 的 PVE 虚拟化云管平台进行系统的梳理与详细剖析。

## 3.1 系统的可行性分析

可行性分析旨在确立平台开发的必要性，并在技术落地、用户操作和经济投入等方面论证系统能否以合理的代价实现预期的业务价值与管理闭环。

### 3.1.1 技术可行性
经过第二章的技术选型论证，本平台所需的技术栈无论在行业应用广度还是社区开源活跃度上都极具可行性。前端方面，Vue 3 与 Vben Admin 为我们提供了高度成熟的单页面应用工程脚手架与丰富的基础组件，并且通过集成 xterm.js 与 noVNC 技术已有非常稳定并被广泛验证的前台沉浸式渲染终端案例；后端层面，Django 5 与 DRF (Django REST Framework) 在提供高性能敏捷开发 API 的同时，得益于 ASGI 异步生态及 Channels 配合 Redis 能够非常从容地应对密集型、长时间挂起的 WebSocket 调度需求。最核心的 PVE 底层能力提取方面，Proxmox 官方亦提供了完整的 REST API 架构规范和详实的开发者文档说明，这使得我们在开发中对于底层通信的黑盒风险基本被完全消除。此外，Paramiko 以及目前主流的开源大语言模型流式 API 接入均有完善的 Python 生态库可供直接集成调用。因此，研发此全功能整合平台在技术层面完全可行并有着高确定性的落地路径。

### 3.1.2 操作可行性
原生的 PVE 平台由于主要面向极客或底层架构工程师，其操作面板相对生硬、充斥着偏向底层硬件的术语（如块设备、LVM-thin 池、Ceph 仲裁等），这对于很多非专业运维出身的初级使用者或者仅需参加虚拟化实操实验的高校学生来说，学习曲线非常陡峭且极易在误操作下发生高危的集群级故障。而重构后的云管平台，重点引入了现代化 Web 响应式设计语言、完善且人性化的表单校验提示，并在关键网络层附带了图形化可拖拽的拓扑交互设计界面。
同时，系统将完全围绕细粒度的 RBAC 角色分离机制运作，让“特定角色对应专属的操作面板视图”。例如，学生角色登入系统后，只能看见属于自己课程的“实验一键进入”卡片与 Markdown 实验报告编辑器，从而彻底在视觉和操作上屏蔽了复杂的网卡、存储池乃至宿主节点的直接暴露。平台这种从“以冰冷硬件为中心”到“以应用角色和对应业务为中心”的操作体验根本性转变，极大降低了用户认知负荷，展现了极高的操作可行性。

### 3.1.3 经济可行性
本方案选用的核心底层技术栈——包括基础的 Debian/Ubuntu 服务器操作系统、Proxmox VE 虚拟化底座引擎、Vue 3 前端框架、Django 5 后端应用服务器以及 MySQL 和 Redis 缓存通信队列，皆为能够提供企业级稳定性且开源免费的产品体系。这彻底规避了在使用如 VMware vSphere 此类商业闭源平台时，随算力规模水涨船高而产生的天价软件授权许可以及后续的昂贵年检维保费用痛点。另外，此私有云平台的超融合特质也意味着能够最大化地榨取普通标准 X86 硬件的算力，通过 LXC 轻量级容器更可以极大地延长老旧学校机房或企业退役测试机群的使用寿命。综上所述，该课题研发无论是从所投入的基础软件许可成本，还是从长期稳定运行所带来的集约化管理效益来看，均展现出极其可观的经济可行性。

## 3.2 功能需求分析

本系统面向多维度复杂的使用群体，既需服务于需要深度掌控底层全局的系统运维架构师与超管，亦要能服务于前台参与教育日常实操与教务管理的师生群体。经综合业务调研，系统需满足以下六大核心子模块的功能需求矩阵：

### 3.2.1 基础虚拟化资源与网络运维需求
1. **PVE 节点与物理算力资源纳管**：系统应支持多台 PVE 物理计算节点的集群统一接入认证，并在管理大盘后台能够直观地以图表化形式呈现出各台宿主机的高可用状态、CPU 利用率、内存消耗情况及集群总体健康度。
2. **底层存储池与模板中心维管**：系统需要具备针对跨节点存储设备及挂载目录的映射与容量用量的检索功能，允许集群管理员上传、查阅并长期维护各类已固化的（如 Ubuntu/CentOS/Windows）操作系统克隆模板体系及 ISO 纯净镜像资源仓库。
3. **基础设施网络架构管理**：平台应支持对底层网卡、各类 Linux 网桥（vmbr）、VLAN 乃至物理级绑定的配置进行统筹操作；能够允许网络工程师进行局域网 IP 子网网段的统一预注册、登记发放与使用率审计池设计，并辅以可视化的图形网卡拓扑生成。

### 3.2.2 实例部署与深度生命周期管理需求
1. **虚拟机 (VM) 与容器 (LXC) 实例批量部署**：系统需打破传统控制台复杂的规格输入，提供通过向导式直观表单勾选，便能完成从计算核心、内存到网卡装配的虚机定制，并能一键向特定宿主节点集群下发批量克隆派系。
2. **实例电源信令与动态状态干预**：针对每一台处于生命周期中的实例，系统要在表格或详情栏提供快捷的如：一键自检开机、无代理 ACPI 优雅重启、强行断电、挂起冬眠或从挂起中恢复恢复、销毁丢弃实例以及创建一致性快照等深度的动作入口。
3. **任务调度队列与失败重试流水**：为了有效化解大规模初始化百台实例时引发的 PVE 底层计算与 IO 瞬时阻塞过载，以及处理诸如夜间批量执行快照与备份的场景；系统强制要求提供任务 (Task) 异步调度流查询面板，允许管理员追踪实时处于排队状态、执行中或发生错误的底层动作流水明细，支持手工挂起与容错重试。

### 3.2.3 控制台终端与可视化监控需求
1. **浏览器内嵌式双轨终端交互接入**：针对 LXC 轻量级容器架构和各类完整的 KVM 强隔离操作系统环境，系统在前端不能依赖任何桌面级第三方客户端下载包。需提供基于标准 HTML5 且支持复制粘贴功能的、安全的文本式 Web SSH 交互对接窗口，以及基于 Canvas 帧渲染穿透的 noVNC 图形化远程桌面一键呼出支持。
2. **高频状态遥测监控大屏设计**：需在登录后的系统最高层级看板页中设计汇总式监控大屏，该屏需能够汇总通过定时器（如每一秒级）拉取并动态刷新的反映 PVE 异构算力集群下各项关键系统性能参数的数据仪表盘（如当前带宽吞吐与集群总 IOPS）与时序折线图趋势。

### 3.2.4 实验教学双角色业务流需求
此领域的需求提炼是将本平台在应用纵深上与其他那些“仅仅只能开机关机”的通用基础云管控软件进行区隔的核心发力点：
1. **教师端的实验派发与批阅流**：设定教师独有角色，使其拥有将制作好的精调“模板机”发布为一堂课程素材的能力。教师能够以特定前台班级为发放单位，将由复数个相互串联的虚拟机构成的复杂实验连带环境，成百上千份地向被授权的学生席位进行精准的一键克隆分发隔离派送；并同时辅以配套对应实验指导书和打分规则的在线同步设计发布。
2. **学生端的一站式实训极简工位**：切分隔离的学生角色登入后，整个系统自动隐去一切无关菜单，需以极简的“操作工作台”形式呈现其名下所关联但待操作的任务集群。学生不再关注机器在哪台 PVE 物理机里，仅需直接点击 Web 的“开始实验”卡片即可唤起对应的终端靶机进行操作试车。
3. **Markdown 在线报告集约与双向评阅能力**：需在实验终端的同级或侧栏配套加入轻量但强大的富文本编辑器（包含对 Markdown 语法及多重编程语言代码块语法高亮着色的深度支持）。学生能够呈现“左半屏虚机 Shell 调试，右半屏记录报告验证截图”的并排工位体验；并在结束后提交归档，随后该实验报告数字资产直接进入教师打分页面的待批阅列表中流转。

### 3.2.5 鉴权、组织架构与系统安全需求
1. **树形化部门与用户人员组织映射**：系统应支持创建包含顶级父节点至多层叶子结点的公司/高校混合组织树（高度兼容高校层面的“院系-教学中心-细分专业-入驻班级”嵌套关系），以此作为人员注册加入管理和划界的最基础单位。
2. **高阶细粒度 RBAC 与路由受控资源树发卡**：所有的系统前台可展现的界面侧边菜单栏、高危敏感操作抽屉入口、甚至单独的电源控制按钮；加上后端每一处存在数据增减改变逻辑的敏感 REST 请求端点，必须能与系统中抽象的“角色(Role)字典”发生相互挂钩订阅。允许一个复杂人员同时穿透拥有由多层角色拼装叠合后的综合权限并网；这保障系统的不同老师与学生账号体系具有极度严格甚至按钮被自动禁用的相互资源调配界限与隔离护城河。
3. **防篡改与强迫追溯的双重审计流水**：在安全等级上系统必须涵盖对两种大类维度的强制旁路流水记录机制——其一是针对业务框架的常规请求日志流（如追踪 X 学号在某天某时刻登录系统、或越位访问了哪些本不在其权限下的大纲接口表单）；其二是更为隐秘的针对服务器底层的接口监控。这种双重互补式的审计监控机制结合，构筑了拦截因恶意侵入造成的虚拟集群失控并能够在事后溯源反查的严密系统的安全防御墙。

### 3.2.6 AI 大模型助手辅助需求
在当前技术日新月异和操作平台日益复杂的双重背景下，初级使用者或学生群体往往对在 Linux 环境内的故障排查及实操命令行心怀恐惧和充满大量同质化重复疑问。因此平台创新性地确立了加入内嵌通用智能问答助手的强需求来大幅卸载教师与管理员的日常“答疑解惑”重负，提升平台的极客属性。
1. **常驻的流式对答界面与灵活的模型集成设置**：平台在前端设计上需使得任何主模块页面的右下角均可随时唤出一个悬浮式对话交互框，其不仅能提供媲美目前主流大模型的打字机流式逐字反馈推演流以消除等待枯燥感，还要在后端提供让实施管理员随时切换不同诸如 OpenAI (ChatGPT)/百川/月之暗面等各大语言模型服务商 API Endpoint 提供网关通道配置界面。
2. **基于 RAG 的闭环领域知识库问答检索赋能**：考虑到通用常识大模型对本套系统独特的教学体系指导书和私有化内网部署规则常常处于完全幻觉或一无所知状态，系统有核心需求去提供一个可以自行录入包含诸如特定平台操作 PDF，课程内部 Word 指导等语料资料模块。以实现在用户提交问询前置流程里能够利用倒排向量相似度搜索出高匹配的知识内容块预先输送给语言大网络上下文以矫正其回复并极大提高回复贴合特定系统内具体步骤规范的高质辅助解答能力。

## 3.3 非功能性需求分析

除了上文详细确立和明确化了的众多具体的功能操作用例以外，为了确保该云系统能够在投产上线后面临极端压载和大规模高并满训发请求突刺的生产考验环境里依然维持健壮的服务质量，平台还需要去满足并向如下这些非功能性设计要求指标做对齐与攻坚：

1. **极端安全性保障要求**
系统应用层框架要必须抵御常规恶意诸如典型的 XSS（跨站恶意脚本）、跨站用户冒充请求伪造 (CSRF防伪票缺漏)、基于 ORM 拼接缝隙的 SQL 逃逸等经典网络入侵行为。为了保护在公共网络或者教育城域大局域网下的链路窃听行为，所有系统的平台与端对端客户端通讯将需依赖标准套接字加密下的 HTTPS/SSL 协议证书封装；特别是其涉及虚拟化终端字符回显敏感通讯的 WebSocket 也必须强制约束在 (WSS) 传输加盖协议下。系统的 Token 和其余诸如集群 ROOT 管理凭证禁止在前台本地被未经脱敏暴露或者明文做非持久生命周期的长滞留风险存放。
2. **全天候高可用性与系统弹性容灾级要求**
本系统的架构后端调度中心任务分配机制即便在所连接部分 PVE Worker 节点不期发生由于物理停电导致的连接丢失或内网心跳通讯大崩溃（类似短时脑裂状态）的情景下，必须做到调度记录数据的最终一致性而非出现全局操作级雪崩奔溃错误堆栈锁死。即要求后台对于处于半分配执行中或者操作超时的任务应当被置入异常中止容错队列供后期二次补偿排队重投；针对原本已经建立的虚机因为意外导致没有关闭或者对于空置未见操作且超规定时效长时间存留的各类占用高资源的 SSH 连接通道进程应带有定时清理死链接监控以确保存活主程运行健康心跳能力。
3. **无缝响应体验与超清全双工承载要求**
当有海量读写 IO 请求因 PVE 底置物理存储盘性能遇到写入排队顶峰阻塞之时，云系统的 UI 前端在异步机制隔离保护下需在最快感官的反馈里提供遮罩排队感知（Loading），绝不要引发在主操控端造成整体无响应等死机痛感。特别地强调在其通过 Web 打开虚拟机黑屏命令行或者由于无缝滑动鼠标的 VNC 连接互动时系统在常规良好的校园或企校局域网环境其指令反传的响应等待不应＞60毫秒极限延迟感。系统内部单一服务器管理进程需验证其最高可抵御百名以上实操终端并发分发指令并且同一秒能处理大批量来自云主机的秒级刷新状态驻留轮询流；绝不可因为拥堵而产出诸如图形数据包黏合卡顿及命令解析丢帧导致的严重的业务阻塞事故。
